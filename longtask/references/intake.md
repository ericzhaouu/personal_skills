# 最多五问的需求澄清

## 问法

先从用户原话填充契约，只问仍缺失且会改变计划的内容。问题采用“目的—取舍—判据”结构，促使用户说明为什么和怎样判断，而不是只索要名词。一次可列出多个编号问题，但整个澄清阶段累计不得超过五个编号；后续追问占用剩余额度。计划确认问题不计入五问。

按缺口从下列问题中选择，不机械地全部询问：

1. **结果：** 如果最终只能保留一个有价值、可交付的结果，它应是什么、给谁使用、采用什么格式？这用于区分真正目标与手段。
2. **范围：** 哪些输入、时间范围或对象必须完整覆盖，哪些明确不应触碰？如果完整度与速度冲突，优先哪一个？
3. **验收：** 一个不了解过程的第三方应依据哪些可观察证据判定成功？要求可核验的数量、质量、覆盖率、测试或样例，而不是“效果好”。
4. **权限与边界：** 允许读写哪些位置，是否允许发送、发布、删除、覆盖、付费、交易或修改外部系统？哪些动作即使计划内也必须逐次确认？
5. **约束与取舍：** 截止时间、并发、模型/成本、保密、来源质量有什么限制？失败时更偏向自动重试、降级交付，还是等待人工决定？

如果前一回答揭示新的关键缺口，用剩余问题追问；不要把一个编号拆成多个伪装问题以绕过上限。五问后仍不明确时采用：只读优先、只写 run 目录、不做外部副作用、不删除/覆盖、较低并发、需要证据的保守假设，并在计划摘要中醒目标注。

## 规范化契约

产出以下字段：

- title
- objective
- audience_and_use
- deliverables：路径/格式/最低内容
- inputs：来源、范围、完整性要求
- scope.in_scope
- scope.out_of_scope
- boundaries.allowed_reads
- boundaries.allowed_writes
- boundaries.forbidden_actions
- boundaries.external_side_effects 与逐次审批规则
- success_criteria：每条含 id、criterion、evidence
- constraints：期限、并发、模型/成本、隐私、优先级
- assumptions：每条说明来源和撤销方式

目标描述使用“完成什么 + 交付给谁/何处 + 边界 + 如何验收”，不把工具或实现步骤误写成目标。
